# AWS X-Ray

- It is a distributed tracing application. It designed to track sessions through an application

> **Status (2026):** The **X-Ray SDKs and X-Ray daemon** entered maintenance mode on **Feb 25, 2026** (security fixes only) and reach **end of support on Feb 25, 2027**. The X-Ray **service** itself stays fully supported. New instrumentation should use **OpenTelemetry** - AWS Distro for OpenTelemetry (ADOT) SDKs/collector or the CloudWatch agent - sending traces to X-Ray / CloudWatch (Application Signals, Transaction Search).
- X-Ray takes data from many services (API Gateway, Lambda, DynamoDB) as part of an application and gives on single overview of the session flow
- Fundamental concepts of X-Ray:
  - **Tracing Header**: when an user connects to an application with X-Ray enabled, a **tracing ID** is generated an embedded into a tracing header. This header is used to track the request across all supported services
  - **Segments**: supported services send data to X-Ray using segments. Segments are data blocks containing host/ip, request, response, work done (times), issues information
  - **Subsegments**: segments can contain subsegments for more granularity. This can contain details to other services as part of the application component
  - **Service Graph**: JSON document detailing services and resources which make up the application
  - **Service Map**: visual representation of a service graph by the X-Ray console
- **Trace**: all segments generated by a single request (same trace ID); header `X-Amzn-Trace-Id` (ALB adds it but does not send segments itself)
- **Annotations**: indexed key/value pairs => usable in **filter expressions** to search traces (e.g. `annotation.customer_tier = "gold"`)
- **Metadata**: non-indexed key/value data (not searchable)
- **Sampling rules**: control how many requests are traced (default: first request each second + 5% of additional requests) - centrally configured in the console, no redeploy needed
- **Groups**: filter expression-based groups of traces, each with its own CloudWatch metrics and insights
- **X-Ray Insights**: anomaly detection on fault rates, notifications via EventBridge
- Traces are retained for **30 days**
- In order to provide X-Ray data to the AWS X-Ray service we can do the following:
  - EC2: install X-Ray Agent (X-Ray daemon, UDP 2000) - today: CloudWatch agent or ADOT collector
  - ECS: agent is installed in any task (daemon/ADOT collector as a **sidecar** container)
  - EKS: ADOT collector (add-on) as DaemonSet/sidecar
  - Lambda: enable X-Ray (**active tracing**), Lambda runs the daemon for you; ADOT Lambda layer for OpenTelemetry
  - Beanstalk: agent is preinstalled
  - API Gateway: can be enabled per stage option
  - SNS and SQS: can be enabled (trace header propagation; SQS => Lambda traces linked)
  - Also: App Runner, Step Functions, EventBridge, AppSync
- Services require IAM permission in order ot send data to X-Ray service (`xray:PutTraceSegments`, `xray:PutTelemetryRecords`, `xray:GetSamplingRules` - managed policy `AWSXRayDaemonWriteAccess`)
- Cross-account tracing: CloudWatch cross-account observability (monitoring account sees traces of source accounts)
- **Transaction Search** (2024): ingests 100% of spans as structured logs in CloudWatch Logs (`aws/spans`) for search/analytics, with indexing of a % of spans as traces - cheaper at scale than X-Ray trace pricing
- **Application Signals** builds on X-Ray/OpenTelemetry traces for APM (service map, SLOs)

## X-Ray Exam Tips

- "Find which microservice adds latency / end-to-end request view" => X-Ray (service map, traces)
- "Search traces by business attribute" => annotations (not metadata)
- "Reduce tracing cost" => sampling rules
- "Vendor-neutral instrumentation / future-proof" => OpenTelemetry / ADOT
- X-Ray = traces; CloudWatch = metrics/logs; CloudTrail = API audit
