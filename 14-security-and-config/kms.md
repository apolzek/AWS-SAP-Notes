# Encryption and KMS

## Encryption Approaches

- **Encryption At Rest**: designed to protect against physical threat or tempering
    - Data is stored in shared hardware in an encrypted form, even if somebody has access to hardware it can not access the data in a readable format
    - General used when one party is involved
- **Encryption In Transit**: aimed to protect data when transferred between 2 places
    - Generally used when multiple individual/systems are involved

## Encryption Concepts

- Plaintext: un-encrypted data, can be text, image, other application, etc.
- Algorithm: peace of code which takes plaintext and a key and generates encrypted data. Examples of algorithms: Blowfish, AES, RC4, DES, RC5 and RC6
- Key: is a password
- Ciphertext: when an algorithm takes the plaintext and the key, the output generated is cyphertext (encrypted data)

## Symmetric Encryption

- Symmetric Keys: the same key can be used for encryption and for decryption as well
- Symmetric encryption algorithms: AES-256
- Great for encryption at rest, not recommended for encryption in-transit

## Asymmetric Encryption

- Makes it much easier to exchange keys
- Asymmetric algorithms: RSA, ElGamal
- Asymmetric Keys: are formed of 2 parts: public key and private key
- A public key can be used to generate cyphertext which can only be decrypted by the private key
- Asymmetric encryption is used by PGP, SSL, SSH, etc.

## Signing

- Process used to prove identity of a message
- A message can be signed with a private key and verified using the public key

## Steganography

- A process to hide encrypted data in plaintext data

## KMS - Key Management Service

- It is a regional and a public service
- Let's us create, store and manage cryptographic keys
- Can handle symmetric and asymmetric keys
- Can perform cryptographic operations such as encryption and decryption
- **Keys never leave KMS!** Keys can be created, imported but they are locked inside KMS
- KMS also provides a FIPS 140-2 (L2) compliance <span style="background-color: Red"><-- REMEMBER THIS</span>
    - **Update (2026):** KMS HSMs are now validated at **FIPS 140-3 Level 3** overall (was 140-2 Level 2 overall, Level 3 in some categories). Older exam material still says "KMS = Level 2, CloudHSM = Level 3" - if a question insists on *single-tenant* HSM / exclusive key control, the answer is still CloudHSM

### KMS Keys (Formerly known mainly as CMK - Customer Master Keys)

- Main things managed by KMS are KMS keys
- They are used by KMS in cryptographic operations
- They are logical containing the following things: ID, date, policy, description and state
- Every KMS key is backed by physical key material. The physical key material can be generated by KMS or imported by KMS
- KMS keys can be used to directly encrypt or decrypt data for up to 4KB of data
- Key spec types: symmetric (`SYMMETRIC_DEFAULT` AES-256-GCM - the only type supported by most AWS service integrations), asymmetric RSA/ECC/ML-DSA (encrypt/decrypt or sign/verify; public key can be downloaded), HMAC keys (`GenerateMac`/`VerifyMac`)

### DEK - Data Encryption Keys

- Data Encryption Keys are generated from KMS keys using `GenerateDataKey` API
- These keys can be used to locally encrypt/decrypt data with size larger than 4KB
- DEK generated is linked to a specific KMS keys
- KMS does not store the DEK in any way, it is generated and provided to the user and it is discarded afterwards
- KMS provides 2 version of the key a plaintext and a ciphertext encrypted with the CMK
- It is expected from us to discard the plaintext key as soon as we encrypted the data
- The encrypted data and the encrypted data encryption key should be stored side by side
- For decryption of the data we pass back to KMS the encrypted DEK to be decrypted and with the decrypted key we decrypt the data itself

### Key Concepts

- KMS keys are isolated to a region and never leave KMS (by default)
- KMS also supports multi-region keys, where keys are replicated to other regions
- There are 3 types of keys:
    - **AWS owned keys**: owned and used by an AWS service across many accounts, not visible in our account, free (e.g. S3 SSE-S3, DynamoDB default)
    - **AWS managed keys** (`aws/s3`, `aws/ebs`, `aws/rds`...): created in our account by a service, we can see them and audit usage in CloudTrail but can't change the key policy, can't rotate manually, **can't be used cross-account** <span style="color: red;">EXAM</span>
    - **Customer managed keys**: created explicitly by the customer, full control of key policy, grants, rotation, deletion, cross-account use ($1/month per key + API calls)
- Customer managed keys are more configurable. For example, we can edit the key policy to allow cross account access to the key
- KMS keys support rotation. Rotation is optional for customer managed keys
    - AWS managed keys: rotated automatically every year (can't change)
    - Customer managed keys: automatic rotation optional, default every 365 days, custom period **90 - 2,560 days**; plus **on-demand rotation** (`RotateKeyOnDemand`, limited number per key)
    - Key ID, ARN, alias and policies stay the same after rotation - no re-encryption of data required
    - Imported key material (BYOK) and keys in custom key stores: **no automatic rotation** - rotate manually by creating a new key and moving the alias (on-demand rotation for imported keys supported since Jun 2025)
    - Asymmetric and HMAC keys: no automatic rotation
- A KMS key contains the backing key, the physical key material and all previous backing keys caused by rotation => data encrypted with previous keys can still be decrypted
- We can create aliases for KMS keys. Aliases are per region (`alias/name`) - point applications at an alias so the underlying key can be changed
- Key policies and security:
    - Key Policies (Resource): they are different compared to policies other AWS services have in the way that each KMS keys policy has to explicitly allow access from the owner AWS account
    - Every KMS keys has a key policy
    - KMS keys are very granular
    - Key policy must allow the account root (`arn:aws:iam::<acct>:root`) for IAM policies to be able to grant access to the key (default key policy does this) - without it, IAM permissions alone don't work <span style="color: red;">EXAM</span>
    - **Grants**: temporary, programmatic delegation of key usage to a principal (used by AWS services e.g. EBS/RDS on our behalf); `CreateGrant`, `RetireGrant`, grant tokens for eventual consistency
    - Condition keys: `kms:ViaService` (allow only via e.g. `s3.eu-west-1.amazonaws.com`), `kms:CallerAccount`, `kms:EncryptionContext:*`, `kms:GrantIsForAWSResource`
    - **Encryption context**: non-secret key/value AAD bound to ciphertext, logged in CloudTrail, required again at decryption
    - Cross-account: key policy in key account allows the other account + IAM policy in the other account allows `kms:Decrypt`/`Encrypt` etc.

### Multi-Region Keys

- Primary key + replica keys in other regions sharing the same key ID (`mrk-` prefix) and key material - data encrypted in one region can be decrypted in another without re-encryption or cross-region calls
- Each replica is an independent resource (own key policy, grants, aliases); rotation is managed on the primary and propagated
- Use cases: global DynamoDB tables / Aurora Global with client-side encryption, DR, multi-region signing, S3 cross-region replication with client-side encryption
- Not global - still regional resources; AWS services that encrypt data (e.g. EBS snapshot copy) usually still re-encrypt with a key in the destination region <span style="color: red;">EXAM</span>

### Key Stores and Key Material Origin

- `AWS_KMS` (default): KMS generates and stores key material in its HSMs
- `EXTERNAL` (**BYOK** - imported key material): we generate key material and import it wrapped with a KMS public key; we can set an expiration and delete it immediately; we're responsible for durability (keep a copy)
- `AWS_CLOUDHSM` (**CloudHSM key store**): key material in our CloudHSM cluster (single-tenant) - see CloudHSM notes
- `EXTERNAL_KEY_STORE` (**XKS**): key material stays in an external key manager/HSM outside AWS, reached via an XKS proxy; we can revoke AWS's access ("hold your own key") at the cost of availability/latency <span style="color: red;">EXAM</span>

### Key Deletion and Quotas

- Deletion is scheduled with a waiting period of **7 - 30 days** (default 30); key is disabled during this time and deletion can be cancelled. Use a CloudWatch alarm on CloudTrail usage of a key pending deletion. Prefer disabling over deleting
- Request quotas: shared per account/region for cryptographic operations (e.g. 5,500 / 10,000 / 50,000+ RPS depending on region for symmetric) - `ThrottlingException` -> use data key caching (Encryption SDK), **S3 Bucket Keys** (reduce S3 -> KMS calls by up to 99%), or request a quota increase <span style="color: red;">EXAM</span>

### Exam Scenarios

- Share an encrypted EBS snapshot/AMI or RDS snapshot cross-account -> must be encrypted with a **customer managed key** shared via key policy (re-encrypt if it uses an AWS managed key)
- Audit who used a key -> CloudTrail (all KMS API calls logged)
- Separate duties: key administrators (manage) vs key users (use) in the key policy
- Encrypt large data -> envelope encryption (`GenerateDataKey`), `GenerateDataKeyWithoutPlaintext` for later use
- AWS Encryption SDK: client-side envelope encryption, multi-region/multi-key keyrings, data key caching
