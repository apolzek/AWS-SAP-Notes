# S3

## S3 Basics and Key Limits

- Object storage, regional service (data never leaves the region unless replicated/copied), bucket names globally unique (general purpose buckets)
- Max object size: **50 TB** (raised from 5 TB in Dec 2025, all storage classes and features)
- Single `PutObject` max: 5 GB => use **multipart upload** above that (recommended > 100 MB), max 10,000 parts, 5 MB-5 GB per part
  - Use a lifecycle rule `AbortIncompleteMultipartUpload` to clean up orphaned parts (they are billed)
- Performance: at least **3,500 PUT/COPY/POST/DELETE** and **5,500 GET/HEAD** requests/sec **per prefix**, no limit on number of prefixes => parallelize across prefixes
  - Multipart upload / byte-range fetches for throughput; `503 Slow Down` => back off and spread prefixes
- **Strong read-after-write consistency** for all PUT/DELETE/LIST operations (since Dec 2020), no extra cost. Exam trap: old "eventual consistency" answers are wrong
- Bucket quota: 10,000 general purpose buckets per account by default, can be raised up to 1 million
- **Conditional writes**: `If-None-Match: *` (create only if key doesn't exist) and `If-Match: <ETag>` (overwrite only if unchanged) => optimistic concurrency without external locking; can be enforced via bucket policy condition keys
- Versioning: Unversioned => Enabled => Suspended (can never go back to unversioned). **MFA Delete** can only be enabled by the root user via CLI/API
- Object Ownership: **Bucket owner enforced** (ACLs disabled) is the default for new buckets since Apr 2023 => use policies, not ACLs. ACLs needed only for legacy cases (e.g. S3 server access logs to old setups)

## Storage Classes

Storage class is defined at the object level, when uploading. If not specified => standard.

- **S3 Standards (default)**:
  - The objects are stored in at least 3 AZs
  - Provides eleven nines of durability (99.999999999%) and 99.99% availability
  - The replication is using MD5 file checks together with CRCs to detect object issues
  - When objects are stored in S3 using the API, a HTTP 200 OK response is provided
  - Billing:
    - GB/month of data stored in S3
    - A dollar for GB charge transfer out (in is free)
    - Price per 1000 requests
    - No specific retrieval fee, no minimum duration, no minimum size
  - S3 standard makes data accessible immediately, can be used for static website hosting
  - Should be used for data frequently accessed
- **S3 Standard-IA**:
  - Shares most of the characteristics of S3 standard: objects are replicated in 3 AZs, durability is the same, availability is 99.9%, first byte latency is the same, objects can be made publicly available
  - Billing:
    - It is more cost effective for storing data
    - Data transfer fee is the same as S3 standard
    - Retrieval fee: for every GB of data there is a retrieval fee, overall cost may increase with frequent data access
    - Minimum duration charge: we will be billed for a minimum of 30 days, minimum capacity of the objects being 128KB (smaller objects will be billed as being 128 KB)
    - Should be used for long lived data where data access is infrequent
- **S3 One Zone-IA**:
  - Similar to S3 standard, but cheaper. Also cheaper than S3 standard IA (~20% less)
  - Data stored using this class is only stored in **one AZ**
  - Billing:
    - Similar to S3 standard IA: similar minimum duration fee of 30 days, similar billing for smaller objects and also similar retrieval fee per GB
    - Same level of durability (if the AZ does not fail)
    - Data is replicated inside one AZ
  - Since data is not replicated between AZs, this storage class is not HA. It should be used for non-critical data or for data that can be reproduced easily (e.g. secondary copies via CRR, thumbnails)
- **S3 Express One Zone** (directory buckets):
  - Single-AZ, highest performance class: single-digit ms latency, up to 10x faster than Standard, hundreds of thousands of requests/sec per bucket, lower request cost
  - Only in **directory buckets** (see below); we choose the AZ => co-locate compute in the same AZ
  - Use cases: ML training, interactive analytics, HPC scratch, high request-rate workloads
  - Not resilient to AZ loss => keep the source of truth elsewhere
- **S3 Glacier Instant Retrieval**:
  - It like S3 Standard-IA, but with cheaper storage, more expensive retrieval, longer minimums
  - Recommended for data that is infrequently accessed (once per quarter), but it still needs to be retrieved instantly (milliseconds)
  - Minimum storage duration charge is 90 days, 128 KB minimum billable size
- **S3 Glacier Flexible Retrieval (formerly knowns as S3 Glacier)**:
  - Same data replication as S3 standard and S3 standard IA
  - Same durability characteristics
  - Storage cost is about 1/6 of S3 standard
  - S3 objects stored in Glacier should be considered cold objects (should not be accessed frequently)
  - Objects in Glacier class are just pointers to real objects and they can not be made public
  - In order to retrieve them, we have to perform a retrieval process (`RestoreObject`):
    - A job that needs to be done to get access to objects
    - Retrievals processes are billed
    - When objects are retrieved for Glacier, a temporary copy is stored (billed at Standard rate) for the number of days specified, then removed. To make it permanent, copy the object to another storage class
  - Retrieval job types:
    - **Expedited**: objects are retrieved in 1-5 minutes, retrieval process being the most expensive (use **Provisioned Capacity** to guarantee expedited availability)
    - **Standard**: data is accessible at 3-5 hours
    - **Bulk**: data is accessible at 5-12 hours, **free** for Glacier Flexible Retrieval
  - Each archived object has 40KB metadata overhead (32 KB billed at Glacier rate + 8 KB at Standard rate) and a 90 days minimum duration for storage => aggregate small files before archiving
  - Glacier should be used for data archival (yearly access), where data can be retrieved in minutes to hours
  - Restore completion can trigger S3 Event Notifications / EventBridge (`s3:ObjectRestore:Completed`)
- **S3 Glacier Deep Archive**:
  - Deep Archive represents data in a frozen state, the cheapest storage in AWS
  - Has a 40KB metadata overhead per object and a 180 days minimum duration for data storage
  - Objects can not be made publicly available, data access is similar to standard Glacier class
  - Restore jobs are longer:
    - **Standard**: up to 12 hours
    - **Bulk**: up to 48 hours
  - No Expedited retrieval
  - Should be used for archival which is very rarely accessed (compliance, tape replacement)
- **S3 Intelligent-Tiering**:
  - It is a storage class containing 5 different tiering a storage
  - Objects that are access frequently are stored in the Frequent Access tier, less frequently accessed objects are stored in the Infrequent Access tier. Objects accessed very infrequently will be stored in either Archive or Deep Archive tier
    - Automatic: Frequent Access => Infrequent Access (30 days no access) => Archive Instant Access (90 days no access)
    - Optional (opt-in): Archive Access (90-730 days) and Deep Archive Access (180-730 days), these require a restore like Glacier
  - We don't have to worry for moving objects over tier, this is done by the storage class automatically. Accessed objects move back to Frequent Access
  - Intelligent tier can be configured, archiving data is optional and can be enabled/disabled
  - There is no retrieval cost for moving data between frequent and infrequent tiers, we will be billed based on the automation cost per 1000 objects
  - No minimum storage duration; objects < 128 KB are not monitored (always billed at Frequent Access tier, no monitoring fee)
  - S3 Intelligent-Tiering is recommended for unknown or uncertain data access usage
- **Reduced Redundancy Storage (RRS)**: legacy, not recommended, never the correct exam answer

## S3 Lifecycle Configuration

- We can create lifecycle rules on S3 buckets which can move objects between tiers or expire objects automatically
- A lifecycle configuration is a set of rules applied to a bucket or a group of objects in a bucket (filter by prefix, tags, object size)
- Rules consist of actions:
  - Transition actions: move objects from one tier to another after a certain time
  - Expiration actions: delete objects or versions of objects
  - Noncurrent version actions: transition/expire noncurrent versions (`NoncurrentDays`, `NewerNoncurrentVersions`)
  - Clean up: expired object delete markers, incomplete multipart uploads
- Objects can not be moved based on how much they are accessed, this can be done by the intelligent tiering. We can move objects based on time passed
- By moving objects from one tier to another we can save costs, expiring objects also will help saving costs
- Transitions between tiers:
  ![Transition between tiers](images/S3StorageClassesLifecycleConfiguration.png)
- Considerations:
  - Files from One Zone-IA can transition to Glacier Flexible, or Deep Archive, **NOT into Glacier Instant retrieval**
  - Transitions only go "down" the waterfall, never back to Standard (use a copy for that)
  - Smaller objects cost more in Standard-IA, One Zone-IA, etc.
  - By default (since Sept 2024) objects **smaller than 128 KB are not transitioned** unless a size filter overrides it
  - An object needs to remain for **at least 30 days in standard tier** before being transitioned to infrequent tiers (objects can be uploaded manually in infrequent tiers)
  - A single rule can not move objects from Standard to IA tiers and then to Glacier tiers immediately. Objects have to stay for at least 30 days in IA tiers before being moved to Glacier by the same rule. In order to overcome this, we can define 2 different rules
  - Each transition has a per-request cost => transitioning millions of tiny objects to Glacier can cost more than it saves
  - Lifecycle actions are asynchronous (can take time) and billing changes as soon as the rule is eligible

## S3 Replication

Replication between source and destination bucket.

- 2 types of replication are supported by S3:
  - Cross-Region Replication (CRR)
  - Same-Region Replication (SRR)
- Both types of replication support same account replication and cross-account replication
- If we configure cross-account replication, we have to define a policy on the destination account to allow replication from the source account
- We can create replicate all objects from a bucket or we can create rules for a subset of objects. We can filter objects to replicate based on prefix or tags or both
- One source can replicate to multiple destinations (multiple rules), with priorities
- We can specify which storage class to use for an object in the destination bucket (default: use the same class)
- We can also define the ownership of the objects in the destination bucket. By default it will be the same as the owner in the source bucket. Cross-account: use **owner override** to make the destination account the owner
- Replication Time Control (RTC): if enabled ensures a 15 minutes SLA replication of objects (99.99% of objects in 15 min, backed by SLA) + replication metrics and events. Without => best-effort
- Replication consideration:
  - By default replication is **NOT retroactive**: only newer objects are replicated after the replication is enabled
  - Versioning needs to be enabled for both source and destination buckets
  - **S3 Batch Replication** (via S3 Batch Operations) can be used to replicate existing objects, objects that previously failed, or objects already replicated (to a new destination). It needs to be specifically configured. If it is not, replication will not be retroactive
  - Replication by default one-way only, source => destination. There is an option to use **bi-directional replication**, but this has to be configured (two rules + **replica modification sync** to also sync metadata changes)
  - Replication is capable of handling objects encrypted with SSE-S3 and SSE-KMS (with extra configuration: KMS key in destination, `kms:Decrypt`/`kms:Encrypt` permissions). SSE-C (customer managed keys) is also supported, historically it was incompatible
  - Replication requires for the owner of source bucket needs permissions on the objects which will be replicated
  - System events will **NOT** be replicated (for example a change made in the bucket by a lifecycle event), only user events
  - Any objects in the Glacier and Glacier Deep Archive will **NOT** be replicated
  - By default, deletes are **NOT** replicated (delete markers). We can enable delete marker replication. **Version-specific deletes are never replicated** (protection against malicious deletes)
  - No chaining: if A => B and B => C, objects from A are not replicated to C
  - Object Lock buckets can be replicated (retention settings replicated as well)
- Replication use cases:
  - SRR:
    - Log aggregation
    - PROD and Test sync
    - Resilience with strict sovereignty
  - CRR
    - Global resilience improvements
    - Latency reduction
    - Compliance (copy in another region / another account for ransomware protection)

## S3 Multi-Region Access Points

- Single global endpoint over buckets in multiple regions, routes requests over the AWS global network (Global Accelerator based) to the lowest-latency bucket
- Combined with CRR (bi-directional) for active-active or active-passive setups
- **Failover controls**: mark regions active/passive and fail over in minutes
- Requests must be SigV4A signed; buckets can be in different accounts
- Exam: "single global endpoint + multi-region S3 + automatic routing/failover" => Multi-Region Access Points

## S3 Encryption

- Buckets aren't encrypted, objects inside buckets are encrypted
- Encryption at rest types:
  - Client-Side encryption: data is encrypted before it leaves the client
  - Server-Side encryption: data is encrypted at the server side, it is sent on plain-text format from the client
- Both encryption types use encryption in-transit for communication
- Server-side encryption is mandatory (since Jan 2023), we cannot store data in S3 without being encrypted
- There are 4 types of server-side encryption supported:
  - **SSE-C**: server-side encryption with customer-provided keys
    - Customer is responsible for managing the keys, S3 managed encryption/decryption
    - When an object is put into S3, we need to provide the key utilized (HTTPS mandatory)
    - The object will be encrypted by the key, a hash is generated and stored for the key
    - The key will be discarded after the encryption is done
    - In case of object retrieval, we need to provide the key again
    - > **Status (2026):** since April 2026 SSE-C is **disabled by default** for new general purpose buckets (and existing buckets in accounts that never used it). Requests with SSE-C get 403 unless re-enabled via `PutBucketEncryption` (`BlockedEncryptionTypes`)
  - **SSE-S3** (default): server-side encryption with Amazon S3-managed keys
    - AWS handles both the encryption/decryption and the key management
    - When using this method, S3 creates a master key for the encryption process (handled entirely by S3)
    - When an object is uploaded an unique key is used for encryption. After the encryption, this unique key is encrypted as well with the master key and the unencrypted key is discarded. Both the key and the object are stored together
    - For most situations, this is the default type of encryption. It uses AES-256 algorithm, they key management is entirely handled bt S3
    - No role separation, no key audit in CloudTrail
  - **SSE-KMS**: Server-side encryption with KMS keys stored in AWS Key Management Service (KMS)
    - Similar to SSE-S3, but for this method the KMS handles stored keys
    - If no key is specified, S3 uses the **AWS managed key** `aws/s3` (created on first use)
    - When new objects are uploaded AWS uses the KMS key to generate individual keys for encryption (data encryption keys). The data encryption key will be stored along with the object in encrypted format
    - We don't have to use the AWS managed key, we can use our own **customer managed key**. We can control the permission on it (key policy), rotation and how it is regulated
    - **Cross-account access requires a customer managed key** (the key policy of `aws/s3` can't be edited) - common exam trap
    - SSE-KMS provides role separation:
      - We can specify who can access the KMS key
      - Administrators can administers buckets but they may not have access to KMS keys
    - Key usage is logged in CloudTrail
  - **DSSE-KMS**: dual-layer server-side encryption with KMS keys, two independent layers of encryption, for compliance requirements (e.g. CNSSP 15)
- Default Bucket Encryption:

  - When an object is uploaded, we can specify which server-side encryption to be used by adding a header to the request: `x-amz-server-side-encryption`
  - Values for the header:
    - To use SSE-S3: `AES256`
    - To use SSE-KMS: `aws:kms`
    - To use DSSE-KMS: `aws:kms:dsse`
  - All Amazon S3 buckets have encryption configured by default, and all new objects that are uploaded to an S3 bucket are automatically encrypted at rest
  - Server-side encryption with Amazon S3 managed keys (SSE-S3) is the default encryption configuration for every bucket in Amazon S3, this can be overridden in a PUT request with `x-amz-server-side-encryption` header
  - Changing the default encryption does NOT re-encrypt existing objects => use S3 Batch Operations (copy in place) to re-encrypt
  - Enforce encryption in transit with a bucket policy `Deny` when `aws:SecureTransport` is `false`

## S3 Bucket Keys

- Each object in a bucket is using a uniq data-encryption key (DEK)
- AWS uses the bucket's KMS key to generate this data-encryption key
- Calls to KMS have a cost and levels where throttling occurs (KMS request quota shared per account/region): 5500/10_000/50_000 requests/sec depending on region
- Bucket keys:
  - A time limited bucket key is used to generate DEKs within S3
  - KMS generates a bucket key and gives it to S3 to use to generate DEKs for each upload, offloading the load from KMS to S3
  - Reduces the number of KMS API calls (up to 99%) => reduces the costs/increases scalability
- Using bucket keys is not retroactive, it will only affect objects after bucket keys are enabled
- Thing to keep in mind after enabling bucket keys:
  - CloudTrail KMS event logs will show the bucket ARN instead of the object ARN
  - Fewer CloudTrail events of KMS will be in the logs (since work is offloaded to S3)
  - Bucket keys work with SRR and CRR; the object encryption settings are maintained
  - If we replicate plaintext to a bucket using bucket keys, the object is encrypted at the destination side; this can result in ETAG changes on the object
  - Not supported with DSSE-KMS

## S3 Presigned URLs

- Is a way to give other people access to our buckets using our credentials
- An IAM admin can generate a presigned URL for a specific object using his credentials. This URL will have an expiry date
- The presigned URL can be given to unauthenticated uses in order to access the object
- The user will interact with S3 using the presigned URL as if it was the person who generated the presigned URL
- Presigned URLs can be used for GET and PUT operations
- Max expiry: 7 days (SigV4) with IAM user credentials; with temporary credentials the URL expires when the credentials expire (whichever is first)

![Presigned URL PUT/GET](images/PresignedPUTGET.png)

- Presigned URLs can be used for giving direct access private files to an application user offloading load from the application. This approach will require a service account for the application which will generate the presigned URLs
- Presigned URL considerations:
  - We can create a presigned ULR for objects we don't have access to (it simply won't work)
  - When using the URL, the permissions match the identity which generated it. The permissions are evaluated at the moment of accessing the object (it might happen the the identity had its permissions revoked, meaning we wont have access to the object either)
  - Do **NOT** generate presigned URLs with an IAM Role, since assuming a role is based on temporary credentials => when they are not valid anymore, the URL stops working.
  - Recommended to use long-term identities such as an IAM user (or keep expiry shorter than the role session)
  - Restrict usage with bucket policy conditions (`aws:SourceIp`, `aws:SourceVpce`, `s3:signatureAge`)

![Presigned URL](images/PresignedURL.png)

- Alternatives: **presigned POST** (browser form uploads with conditions), **CloudFront signed URLs/cookies** (for content delivered via CloudFront, many files)

## S3 Select and S3 Glacier Select

> **Status (2026):** S3 Select and S3 Glacier Select are **closed to new customers** since July 25, 2024 (existing customers can keep using them). Alternatives: Amazon Athena, Redshift Spectrum, client-side filtering, S3 Tables + query engines.

- Are ways to retrieve **parts** of objects instead of **entire** objects
- S3 can store huge objects (up to 50 TB)
- Retrieving a huge objects will take time and consume transfer capacity
- S3/Glacier provides services to access partial objects using SQL-like statements to select parts of objects
- Up too 400% faster and 80% cheaper
- Both S3 Select and Glacier selects supports the following formats: CSV, JSON, Parquet, BZIP2 compression for CSV and JSON

## S3 Access Points

- Improves the manageability of objects when buckets are used for many different teams or they contain objects for a large amount of functions
- Access Points simplify the process of managing access to S3 buckets/objects
- Rather than 1 bucket policy => we can create many access points with different policies
- Each access point can be limited from where it can be accessed, and each can have different network access controls (**VPC-only access points** => reachable only from a given VPC)
- Each access point has its own endpoint address (DNS address) and an alias usable anywhere a bucket name is expected
- We can create access point using the console or the CLI using `aws s3control create-access-point --name < name > --account-id < account-id > --bucket < bucket-name >`
- Any permission defined on the access point needs to be defined on the bucket policy as well. We can do delegation, by defining wide access permissions in the bucket policy and granular permissions on the access point policy (e.g. bucket policy: allow when `s3:DataAccessPointAccount` = our account)
- BOTH bucket policy + access point policy need to pass to have access
- Access points can also be created for **directory buckets** and attached to **FSx for NetApp ONTAP / FSx for OpenZFS** volumes (access file data with S3 APIs, without moving it)
- Cross-account access points: access point in one account, bucket in another

## S3 Access Grants

- Maps identities (IAM principals or **IAM Identity Center users/groups** from a corporate directory such as Entra ID/Okta) to S3 prefixes/buckets with READ/WRITE/READWRITE grants
- Apps call `GetDataAccess` to get temporary, scoped credentials
- Scales better than bucket policies (policy size limit 20 KB) for thousands of users; access is logged in CloudTrail with the end-user identity
- Exam: "grant directory users/groups access to S3 prefixes at scale" => Access Grants

## S3 Object Lock

- Object Lock can be enabled at the bucket level (on new buckets, or on existing buckets with versioning enabled)
- Versioning will be also enabled when Object Lock is enabled
- Object Lock **CANNOT** be disabled, versioning can not be suspended when Object Lock is active on the bucket
- Object Lock is a Write-Once-Read-Many (WORM) architecture: when an object is written, can not be modified. Individual versions of objects are locked
- There are 2 ways S3 manages object lock:
  - Legal Hold: enabled/disabled = no changes until legal hold is removed (no retention period defined), requires `s3:PutObjectLegalHold`
  - Retention (2 modes): enabled/disabled for a retention period => new object versions protected from being deleted or overwritten
    - Governance: users with specific IAM permissions (`s3:BypassGovernanceRetention` + header `x-amz-bypass-governance-retention`) can overwrite during retention period
    - Compliance: no one can overwrite during retention period (and no changes to the retention settings, **also root user**)
- Object Lock retentions can be individually defined on object versions, a bucket can have default Object Lock settings
- Retention periods can be extended, not shortened (compliance mode)
- Meets SEC 17a-4, FINRA, CFTC requirements. Glacier vault equivalent: **Vault Lock**
- Exam: "WORM, nobody including root can delete for N years" => Object Lock **Compliance** mode

## S3 Block Public Access

- The Amazon S3 Block Public Access feature provides settings for access points, buckets, and accounts to help manage public access to Amazon S3 resources
- **Enabled by default for all new buckets** (since Apr 2023). Account-level settings override bucket-level ones; can be enforced across an Organization (account-level setting + SCP denying `s3:PutAccountPublicAccessBlock`)
- The settings we can configure with the Block Public Access Feature are:
  - **BlockPublicAcls**: rejects PUT requests that include public ACLs (new public ACLs can't be created/modified). Existing ACLs are not affected
  - **IgnorePublicAcls**: S3 ignores all public ACLs (existing and new) on the bucket and its objects, they have no effect
  - **BlockPublicPolicy**: This prevents a bucket policy containing public actions from being created or modified on an S3 bucket, the bucket itself will still allow the existing policy
  - **RestrictPublicBuckets**: if the bucket has a public policy, access is restricted to AWS service principals and authorized users within the bucket owner's account (cross-account and anonymous access blocked)

## S3 Cost Saving Options

- S3 Select and Glacier Select: save in network a CPU cost by retrieving ony the necessary data (closed to new customers)
- S3 Lifecycle Rules: transition objects between tiers
- S3 Intelligent-Tiering for unknown access patterns
- Compress objects to save space
- Use S3 Storage Lens / Storage Class Analysis to find candidates for transitions
- Use **gateway VPC endpoints** (free) instead of NAT Gateway for S3 traffic from VPCs
- S3 Requester Pays:
  - In general, bucket owners pay for all Amazon S3 storage and data transfer costs associated with their bucket
  - With Requester Pays buckets, the requester instead of the bucket owner pays the cost of the request and the data download from the bucket
  - The bucket owner always pays the cost of storing data
  - Helpful when we want to share large datasets with other accounts
  - Enabled as a bucket setting; requesters must include the `x-amz-request-payer` header (or `--request-payer` in CLI) and must be authenticated (no anonymous access)
  - If an IAM role is assumed, the owner account of that role pays for the request!

## S3 Transfer Accelerate

- Used to transfer files into S3. Enables fast, easy, and secure transfers of files over long distances between our client and an S3 bucket
- Takes advantage of the globally distributed edge locations in Amazon CloudFront
- We might want to use Transfer Acceleration on a bucket for various reasons:
  - We upload to a centralized bucket from all over the world
  - We transfer gigabytes to terabytes of data on a regular basis across continents
  - We can't use all of our available bandwidth over the internet when uploading to Amazon S3
- To use Transfer Accelerate, it must be enabled on the bucket. After we enable Transfer Acceleration on a bucket, it might take up to 20 minutes before the data transfer speed to the bucket increases
- Uses a distinct endpoint `<bucket>.s3-accelerate.amazonaws.com`; bucket name must be DNS compliant without dots
- Billed only when it actually accelerates the transfer. Can be combined with multipart upload
- Not supported on directory buckets

## Hosting Static Site on S3

- We can host a static site on S3
- To host a static site in a bucket we must enable static website hosting, configure an index document, and set permissions
- We should also make a bucket content public:
  - We should turn of Block Public Access settings
  - We should attach a bucket policy which allows public read on the objects
- Amazon S3 website endpoints do not support HTTPS! If we want to use HTTPS, we can use Amazon CloudFront to serve a static website hosted on Amazon S3
- Best practice: keep the bucket private, use the S3 REST endpoint as CloudFront origin with **Origin Access Control (OAC)** (OAI is legacy). OAC can't be used with the website endpoint (custom origin)
- Bucket name must match the domain name when using Route 53 alias directly to the website endpoint
- CORS configuration needed when a site in one origin loads resources from another bucket

## S3 Events and Monitoring

- **S3 Event Notifications**: targets SNS standard topics, SQS standard queues, Lambda (FIFO queues/topics not supported as direct targets), or **Amazon EventBridge** (all events, advanced filtering, multiple targets, archive/replay)
- **CloudTrail**: management events by default; data events (GET/PUT object) must be enabled (cost)
- **Server access logs**: best effort, delivered to another bucket (never log into the same bucket => loop)
- **S3 Storage Lens**: org-wide visibility of usage/activity, cost optimization and data protection recommendations; free metrics + advanced metrics (prefix-level, CloudWatch publishing, 15 months history); can export to S3 Tables
- **S3 Inventory**: daily/weekly CSV/ORC/Parquet list of objects and metadata (encryption, replication status) => input for Batch Operations, query with Athena
- **S3 Metadata**: automatically maintained, queryable Apache Iceberg tables (in S3 Tables) with object metadata
  - Journal table: near real-time record of changes (uploads, deletes, metadata changes)
  - Live inventory table: up-to-date view of all objects, including existing ones (backfilled)
  - Query with Athena, Redshift, EMR, QuickSight - replaces custom metadata indexes in DynamoDB

## S3 Batch Operations

- Run a single operation on billions of objects: copy (e.g. re-encrypt, change storage class), invoke Lambda, replace tags/ACLs, restore from Glacier, Object Lock retention/legal hold, Batch Replication
- Input: S3 Inventory report, CSV manifest or generated manifest from filters
- Managed retries, progress tracking, completion report
- Exam: "encrypt all existing unencrypted objects" => S3 Inventory + Batch Operations (copy)

## Directory Buckets and S3 Express One Zone

- Bucket type for S3 Express One Zone (single AZ) and Dedicated Local Zones
- Hierarchical namespace (prefixes are real directories), name format `bucket--azid--x-s3`
- Session-based authorization (`CreateSession`) for low-latency auth
- Features: append to existing objects, atomic `RenameObject`, access points, S3 Inventory, CloudWatch request metrics, lifecycle expiration
- No versioning, no Object Lock, no replication => not for durable source-of-truth data
- Can be used as a cache layer in front of a general purpose bucket (e.g. Mountpoint caching)

## S3 Tables

- **Table buckets** purpose-built for Apache Iceberg tabular data (Parquet), up to 3x faster queries and 10x more TPS vs self-managed Iceberg tables in general purpose buckets
- Automatic table maintenance: compaction, snapshot management, unreferenced file removal
- Integrates with AWS Glue Data Catalog / Lake Formation => Athena, Redshift, EMR, QuickSight, Spark
- Replication of tables (cross-region/cross-account, read-only replicas) and Intelligent-Tiering for tables (since Dec 2025)
- Exam: "managed Iceberg tables on S3 with automatic compaction" => S3 Tables

## S3 Vectors

- **Vector buckets** with vector indexes: native storage and similarity search for embeddings, sub-second queries, up to ~90% cheaper than dedicated vector DBs
- GA Dec 2025: up to 2 billion vectors per index, 10,000 indexes per vector bucket, up to 4,096 dimensions, metadata filtering
- Integrates with Amazon Bedrock Knowledge Bases (RAG) and Amazon OpenSearch Service (tier cold vectors to S3, hot in OpenSearch)
- Use when: large, infrequently queried vector datasets with cost focus. Use OpenSearch for very low latency / high QPS

## Mountpoint for Amazon S3

- Open-source file client that mounts an S3 bucket as a local file system on Linux (also EKS via Mountpoint CSI driver)
- High throughput for read-heavy workloads (ML training, analytics), sequential writes of new files
- **Not POSIX-complete**: no in-place modification of existing files, no file locking, no symlinks, rename limited => if a full shared POSIX file system is needed, use EFS/FSx
- Supports caching (local disk or S3 Express One Zone)

## Glacier (vault-based service)

> **Status (2026):** the original standalone Amazon Glacier service (vaults, archives, Glacier API) stopped accepting new customers on Dec 15, 2025. Existing data remains accessible. For new archives use the **S3 Glacier storage classes** in S3 buckets.

- Vault Lock: WORM policy on a vault, immutable once locked (equivalent of S3 Object Lock)

## When to Use What (exam)

- Frequent access => Standard; unknown pattern => Intelligent-Tiering; infrequent but ms access => Standard-IA / Glacier Instant Retrieval (quarterly)
- Reproducible infrequent data => One Zone-IA; ultra low latency, single AZ compute => Express One Zone
- Archive, minutes/hours => Glacier Flexible; archive 12/48h, cheapest => Deep Archive
- Global upload speed => Transfer Acceleration; global single endpoint/failover => Multi-Region Access Points
- WORM compliance => Object Lock Compliance; prevent public data org-wide => account-level Block Public Access + SCP
- Many teams on one bucket => Access Points; directory users at scale => Access Grants
- Sensitive data discovery in S3 => Amazon Macie
