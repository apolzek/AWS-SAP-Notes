# The 7R's of Cloud Migrations (formerly 6R's)

- Are a set of different strategies of migrating systems into the cloud. AWS originally defined 6 (based on Gartner's 5Rs), now **7Rs** with **Relocate** added
- Starting point of a migration is the _discover_, _assess_ and _prioritize_ all the applications to migrate
- AWS migration phases: **Assess** (business case, TCO) => **Mobilize** (landing zone, skills, detailed portfolio discovery, migration plan) => **Migrate and Modernize** (waves)
- Once we have done this, there are 7 different ways of doing migrations:
  - **Rehosting**: lift and shift
  - **Replatforming**: lift and shift with optimizations
  - **Repurchase**: migrate the application while using something newer, example SaaS
  - **Refactoring / Re-architecting**: take advantage of the feature offered by the cloud
  - **Retire**: dump the applications which are no longer needed
  - **Retain**: do not migrate the application, not worth the time and money or it is too scary to migrate
  - **Relocate**: move infrastructure to the cloud without buying new hardware, rewriting apps or changing operations (hypervisor-level lift and shift)

| Strategy | Effort | Cloud benefit | Typical AWS tools |
|---|---|---|---|
| Retire | Lowest | Cost saving | Discovery data (AWS Transform discovery, ADS) |
| Retain | None | None | - |
| Relocate | Low | Low-medium | VMware Cloud on AWS, Amazon EVS, AWS Transform for VMware |
| Rehost | Low | Low-medium | AWS Transform MGN (formerly MGN), VM Import/Export |
| Replatform | Medium | Medium | DMS, Elastic Beanstalk, RDS, App2Container |
| Repurchase | Medium | High (operations) | AWS Marketplace, SaaS |
| Refactor | Highest | Highest | Lambda, containers, AWS Transform (.NET, mainframe, Java) |

## Rehosting

- Lift and shift or migrate as is: move the application with the least amount of changes into the cloud
- Generally used with legacy or monolithic applications
- Reasons to do application rehosting:
  - Reduce admin overhead using IaaS
  - Potentially easier to optimize the application when is running in the cloud compared to working with legacy tooling
  - Cost savings, consuming a certain type of instances
- Negatives:
  - We won't be able to take advantage of the full Cloud offerings
  - Potentially "kicking the can down the road" - delaying what we can do today until tomorrow
- For doing rehosting we can use **AWS Transform MGN** (Application Migration Service, renamed June 2026) or VM Import/Export
  > **Status (2026):** Server Migration Service (SMS) was discontinued in March 2022 and CloudEndure Migration was also retired - MGN is the answer for rehost
- Rehost is the fastest way to exit a data center (contract end, deadline) => "migrate fast, optimize later"

## Replatforming

- Similar to rehosting with the addition of applying certain optimizations to the applications as part of the migration process
- We might decide to use RDS instead of self-managed database instances
- We might use ELBs instead of self managed load balancers
- We might use S3 as a backup or media storage
- We might move to containers (ECS/EKS) with App2Container, or to Elastic Beanstalk
- We might move from commercial engines to managed open source (Oracle => Aurora PostgreSQL) using DMS + Schema Conversion
- Replatforming approach brings no real negatives but also no world-changing benefits
- Potential benefits of migration:
  - Admin overhead reduction
  - Performance benefits
  - More effective backups
  - Improved HA/FT

## Repurchasing

- Unless we have a reason to use self-managed application, we would rather use XaaS (Anything as a Service) products
- Examples of this kind of migrations:
  - MS Exchange => Microsoft 365
  - Self managed CRM => SalesForce
  - Self managed payroll => Xero
- Using a managed service reduces admin overhead, costs and risks. Almost always a preferred option
- Also called "drop and shop"; AWS Marketplace can be used to buy licenses/SaaS
- Watch out for: data migration, integration, licensing (BYOL vs license included), user retraining

## Refactoring / Re-architecting

- Requires a full review of the architecture of an application
- Adopting cloud-native architecture and products
- We might look at adopting service-origin and microservice based architectures
- We might adopt a more API based architecture, event-driven architecture or serverless architecture
- This approach is initially very expensive and time-consuming
- In the long term it does offer the best benefits compared to other types of migrations
- Running a cloud-native application is often cheaper, much more scalable, has better HA/FT, costs are aligned with app usage
- Driven by strong business need: features, scale, performance not achievable in the current architecture
- Patterns: strangler fig (incrementally replace parts of the monolith behind an API/proxy), decompose by business capability, event-driven
- Tools: AWS Transform (agentic AI for .NET, mainframe, VMware, Java modernization), Migration Hub Refactor Spaces (strangler fig routing; closed to new customers since Nov 7, 2025)

## Retire

- Systems are often running for no reasons
- Auditing their usage is often more work than leaving them to run
- A migration is perfect time to re-evaluate the usefulness of an application. If we don't need it, we should switch if off
- Often saves 10% to 20% of costs in case of large scale migration
- Identify candidates with discovery data: low/zero utilization, no inbound connections

## Retain

- Essentially do nothing
- For some application the usage is uncertain with some complicating factors against being able to retire it or migrate it to the cloud
- In other cases some old applications might have some usage, but it wont worth the effort to move them to the cloud
- Or we might have a complex application - leave it till later
- Super-import application - risky to move
- The best advice is to complete the migration of other applications and swing back to focus on the left-overs
- Other reasons: recent hardware investment, latency/compliance/data residency requirements, mainframe dependencies, unsupported licensing
- Hybrid options for retained workloads: Outposts, Direct Connect, Storage Gateway

## Relocate

- Move a large number of servers at hypervisor level, without converting VMs and without changing operations/tools
- Examples: VMware vSphere on-prem => **VMware Cloud on AWS** or **Amazon Elastic VMware Service (EVS)** using VMware HCX; on-prem containers => EKS/ECS
- No new hardware, no application changes, keeps existing VMware licensing and operational model
- Exam keyword: "move VMware workloads quickly with no changes to the VMs and keep existing VMware tools" => Relocate

## Assessment and Planning Tools

- **AWS Transform** (2025): agentic AI service for discovery, assessment, wave planning, network conversion and migration (VMware, Windows/.NET, mainframe). Replaces Migration Hub for new customers
- **Migration Evaluator** (formerly TSO Logic): business case / TCO, right-sizing and licensing (BYOL vs license-included) based on on-prem utilization data; assessment capabilities now also in AWS Transform
- **AWS Application Discovery Service** / **Migration Hub**:
  > **Status (2026):** both closed to new customers since Nov 7, 2025 (existing customers can still use them, no new features). Use AWS Transform
- **AWS Migration Acceleration Program (MAP)**: methodology, partner support and funding/credits for large migrations
- **AWS Prescriptive Guidance**: patterns and playbooks per migration strategy

## Exam Tips

- Deadline/data center exit, little time => Rehost (MGN)
- "Minimal changes but reduce operational overhead" => Replatform (e.g. DB to RDS/Aurora)
- "Move to SaaS" => Repurchase
- "Need scalability/agility that current architecture cannot provide" => Refactor
- "Application not needed / no users" => Retire
- "Recently upgraded / compliance prevents move" => Retain
- "VMware workloads without changes" => Relocate
